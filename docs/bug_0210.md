## BUG-22: 2026-05-13 scheduler start looked successful, but `run_server.py` did not actually start

- Symptom:
  - scheduled run appeared to launch
  - `app_20260513.json` was missing
  - downloads for that date were not processed on time
- Root cause:
  - fragile `Start-Process` output redirection and weak post-start verification
  - the scheduler log could show completion without proving the server actually bound `5081`
- Recovery:
  - missing files were recovered manually later
- Follow-up:
  - startup verification later grew to include pid, listener, and app-log checks

## BUG-23: stale runtime residue and duplicate ownership could break automatic operation after restart

- Symptom:
  - restart sequence completed only partially
  - stale `run_server.pid`, `v11.lock`, and zombie `msedgedriver` caused follow-up failures
  - automatic ownership of the runtime could become ambiguous after restart
- Root cause:
  - restart paths did not fully clean operational residue
  - stale files and living processes could disagree about who actually owned the automation
- Recovery lesson:
  - cleanup must include pid/lock files and driver processes, not just scheduled stop

## BUG-24: manual and helper batch paths could leave misleading wait-state windows and complicate recovery

- Symptom:
  - operator-facing cmd windows could remain open and look like part of the failure
  - manual and helper paths could overlap with automation operation
- Root cause:
  - helper batch files historically used interactive waits such as `pause`, `choice`, or `Read-Host`
  - manual and automated paths were not always clearly separated
- Follow-up:
  - helper paths were moved toward non-interactive defaults, with prompt behavior gated behind explicit manual mode

## BUG-25: PID-file-first logic could miss a live server and trigger duplicate or unnecessary restart behavior

- Symptom:
  - if `run_server.pid` was stale or missing, startup could still try to bring up a new instance even when `5081` was already in use
  - runtime ownership then became harder to reason about
- Root cause:
  - startup logic trusted pid-file state too early
  - actual listener ownership was not always the first source of truth
- Follow-up:
  - listener-first checks and pid re-synchronization became part of the recovery direction

## BUG-26: `localhost` WebDriver/browser reconnect timeout could stop timely downloads

- Symptom:
  - repeated browser reconnect failure while the process itself was not yet fully dead
  - download cycles appeared stalled even though the server process had not completely disappeared
- Example log theme:
  - `Browser reconnect failed: Edge debug port 9333 is not available`
  - `HTTPConnectionPool(host='localhost', port=xxxxx): Read timed out`
- Root cause:
  - WebDriver/browser communication could timeout during cycle execution or reconnect
- Impact:
  - timed download processing could stop until browser connectivity was restored

## BUG-27: download loss could be misdiagnosed when the browser was redirected to the login page

- Symptom:
  - actionable row counts suddenly dropped to zero
  - logs showed list-page requests ending up at `login.jsp?returl=...`
- Root cause:
  - the Youngrim login session had expired or the browser reopened without a usable logged-in state
- Important distinction:
  - in this case, the downloader logic ran, but it was reading the wrong page content
- Immediate recovery:
  - restore the login session in the dedicated `9333` Edge window
  - confirm the next cycle stays on the actual list page

## BUG-28: a non-Youngrim Edge instance could occupy port `9333` and block scheduled startup

- Symptom:
  - scheduled startup failed or aborted even though port `9333` was already listening
  - on affected days, downloads could stop for the whole cycle
- Root cause:
  - a different Edge instance, not using `YoungrimAutoEdgeProfile`, occupied the debug port
- Protection:
  - scheduler validates the owning command line and refuses to reuse the wrong profile
- Remaining risk before later fixes:
  - startup could be blocked correctly, but recovery/alerting was still too weak

## BUG-29: 2026-07-22 to 2026-07-23 overnight outage was amplified by outside-window skip, Edge startup delay, and short recovery timeout

- User symptom:
  - downloads appeared to stop around `2026-07-22`
- Confirmed logs:
  - watchdog from `2026-07-23 00:03` repeatedly reported:
    - `run_server.pid missing`
    - `server port 5081 not listening`
    - missing app log
    - stale health
  - morning scheduler runs repeatedly failed with:
    - `Edge debug port 9333 did not become ready within 30s`
- Root cause combination:
  - watchdog skipped full recovery outside the configured recovery window
  - Edge startup was slower than the old 30-second wait budget
  - watchdog gave `RESTART_CLEAN.bat` only 10 seconds before timeout
- 2026-07-27 remediation:
  - Edge wait increased to `60s`
  - server wait increased to `60s`
  - app log wait increased to `90s` in restart flow
  - one retry added after Youngrim-profile cleanup
  - watchdog full restart timeout increased to `180s`
  - same-day stdout/stderr overwrite avoided by `HHMMSS` suffix
  - outside-window reduced recovery added so watchdog can trigger `V10_AutoStart` without running full `RESTART_CLEAN`

## BUG-30: Edge debugger attach could hang on a profile with extension/state contamination even when `9333` and `msedgedriver` were both healthy

- Symptom:
  - `webdriver.Edge(... debuggerAddress=127.0.0.1:9333 ...)` hung for roughly `120s`
  - logs showed `HTTPConnectionPool(host='localhost', port=xxxxx): Read timed out`
  - direct `9333` checks still showed `main.jsp` alive and logged in
- Confirmed reproduction on 2026-07-27:
  - `msedgedriver 150.0.4078.99` worked with `--version`
  - standalone driver startup on a fixed port reported ready for new sessions
  - direct attach against the active `9333` browser still timed out during `POST /session`
  - after switching to a fresh no-extension profile on `9444`, the same minimal Selenium attach succeeded and the session closed cleanly
- Root cause:
  - the existing Edge automation profile had become unsafe for debugger attach because of accumulated extension/runtime state
  - this was not a simple driver-version mismatch and not explained by `9333` being closed
- Recovery direction:
  - move automation to a dedicated no-extension profile
  - launch Edge with `--disable-extensions`
  - treat the old profile as corrupted and preserve it separately instead of continuing reuse

## BUG-31: log-stamped `2026-07-28` first recovery cycle missed the backlog because login redirect and upload batch limit left `READY` files stranded

- Symptom:
  - after restart, the first download cycle did not backfill the stalled `2026-07-24` to `2026-07-27` range
  - a later partial upload succeeded, but `READY` files remained in local state and were not reflected in `Sheet5`
- Confirmed behavior on 2026-07-28:
  - the downloader was not limited to "today only"; it queried a rolling 7-day window (`start_date=2026-07-21`, `end_date=2026-07-28`)
  - the first cycle hit `login.jsp?returl=...estimate_list.jsp...` and found `0 actionable rows`
  - later processing downloaded backlog files, but `2026-07-24` and `2026-07-27` items remained in `READY`
  - before manual drain, local state showed:
    - `2026-07-24`: `COMPLETED 1`, `READY 9`
    - `2026-07-27`: `READY 5`
  - manual upload drain completed those 14 files and logged them to `Sheet5` at `2026-07-28 07:36:51`
- Root cause combination:
  - the no-extension debug Edge was not in a valid logged-in Youngrim OMS session for the first recovery cycle
  - `auto_upload()` stopped once accumulated parsed rows would exceed `MAX_ROWS_PER_UPLOAD = 300`
  - remaining `READY` files were left for the next cycle instead of being drained in the same cycle
- Recovery:
  - operator restored login in the dedicated debug Edge
  - backlog `READY` files were uploaded manually in one batch (`14` files, `482` rows)
- Code fix:
  - `run_server.py` now drains `READY` files across repeated upload batches in the same cycle
  - new `drain_ready_uploads()` continues until `READY=0` or upload progress stalls
  - this keeps the `300`-row batch cap while preventing silent carry-over of leftover backlog files

## BUG-32: a hung Edge debug session could look healthy because `9333` stayed open while Selenium control was already dead

- Symptom:
  - the dedicated Youngrim Edge window showed `Not Responding`
  - `run_server.py` stayed alive and sometimes kept sleeping, but download/upload cycles no longer completed
  - `START_SCHEDULED.bat` could wrongly reuse that Edge because `9333` was still listening
  - stale `run_server.pid` could also be reused even when `5081` was no longer listening
- Confirmed evidence on `2026-08-11`:
  - `09:25:13` cycle started
  - repeated local WebDriver timeouts followed:
    - `ReadTimeoutError("HTTPConnectionPool(host='localhost', port=50116): Read timed out. (read timeout=120)")`
  - `09:35:21`:
    - `Browser connection appears dead. Reconnecting now...`
  - `09:57:02`:
    - `Browser reconnect failed: cannot connect to microsoft edge at 127.0.0.1:9333`
  - despite that, the process remained alive and entered sleep with `last_cycle_completed_at=None`
  - at `13:28`, stale startup logic still tried to reuse `run_server.py PID 237980` even though `5081` was not actually listening
- Root cause combination:
  - Edge debugger/renderer session could hang without closing the debug port
  - existing health/reuse logic trusted listener state too much
  - startup also trusted pid-file state too much when listener truth disagreed
- Fix on `2026-08-11`:
  - added `edge_debug_probe.py`
  - `START_SCHEDULED.bat` and `RESTART_CLEAN.bat` now probe `/json/version` and `/json/list` before reusing or accepting a `9333` Edge session
  - probe also requires a Youngrim OMS tab, so a dead or wrong browser session is no longer accepted as healthy
  - `START_SCHEDULED.bat` no longer reuses `run_server.pid` when `5081` is not actually listening; it kills the stale PID and starts fresh
  - common Youngrim-noext cleanup logic was factored into both restart flows
- Verified recovery result:
  - fresh Edge session: PID `46360`
  - fresh server session: PID `78564`
  - `2026-08-11 13:29:57` Edge connected
  - `2026-08-11 13:30:04` Google Sheets connected
  - `2026-08-11 13:31:07` cycle completed with:
    - `28 rows / 6 files -> Google Sheets complete`
  - this confirmed the real blocker was the hung Edge session and stale reuse path, not the downloader date window itself

## BUG-33: DevTools-only health checks still allowed `9333` sessions that Selenium could not attach to

- Symptom:
  - the dedicated Edge session could still expose `9333` and respond to DevTools JSON
  - but `run_server.py` startup still failed with:
    - `session not created: cannot connect to microsoft edge at 127.0.0.1:9333`
    - `from chrome not reachable`
  - watchdog then observed repeated half-alive states where only Edge remained
- Confirmed evidence on `2026-08-12`:
  - repeated watchdog failures included:
    - `run_server.pid missing`
    - `server port 5081 not listening`
    - `half-alive state: Edge port 9333 ... server port 5081 down`
  - `run_server_stderr_20260812_140006.log` showed the attach failure explicitly
  - exit snapshots at `09:40:37`, `12:43:22`, and `15:02:24` confirmed that the processing server was genuinely gone during those windows
- Root cause:
  - a debugger session could be healthy enough for `/json/version` and `/json/list`, but still unhealthy for actual Selenium attach
  - this left a gap between "DevTools reachable" and "automation usable"
  - watchdog also cut off `RESTART_CLEAN` too aggressively at `180s`, even though Edge teardown and revalidation often consumed much of that time
- Fix on `2026-08-12`:
  - added `edge_attach_probe.py` to test a real Selenium attach against `debuggerAddress=127.0.0.1:9333`
  - `START_SCHEDULED.bat` and `RESTART_CLEAN.bat` now require:
    - DevTools probe success
    - Selenium attach probe success
  - watchdog default `RESTART_CLEAN` timeout increased from `180s` to `420s`
- Operational conclusion:
  - future health/reuse decisions must treat "attach success" as the real gate, not "port open" alone

## BUG-34: even after attach-probe hardening, a stuck Youngrim Edge session could still survive cleanup and keep re-triggering `chrome not reachable`

- Symptom:
  - `run_server.py` could newly bind `5081`, but the first real browser attach still failed
  - the dedicated Edge session on `9333` remained present while automation was unusable
  - watchdog then kept reporting:
    - `run_server.pid missing`
    - `server port 5081 not listening`
    - `half-alive state: Edge port 9333 ... server port 5081 down`
- Confirmed evidence on the next live recovery cycle after BUG-33 hardening:
  - scheduler showed:
    - `Edge attach probe failed for fresh_launch_attempt_2`
  - latest `run_server_stderr` showed:
    - `session not created: cannot connect to microsoft edge at 127.0.0.1:9333`
    - `from chrome not reachable`
  - a subsequent recovery eventually succeeded only after the stuck Youngrim debug Edge session was explicitly cleared and startup was retried again
- Current understanding:
  - attach-probe hardening correctly detects the bad state, but it does not fully prevent that state from reappearing
  - the remaining weakness is not detection alone, but reliable disposal of the bad Edge session and guaranteed clean replacement
- Still unresolved:
  - watchdog alert delivery remained broken with repeated `HTTP 403`
  - host/log date drift was also observed, making exact incident chronology harder to trust

## BUG-35: host/log date drift can place incident evidence one day ahead of the expected operational date

- Symptom:
  - the expected operational date was still `2026-08-12`, but live logs and host time were observed as `2026-08-13`
  - this made fresh incidents appear to belong to a future day relative to the expected operating timeline
- Impact:
  - incident triage becomes confusing because scheduler, watchdog, health, and stderr logs no longer align with the expected business date
  - backlog judgment and "today vs yesterday" reasoning can become error-prone even when automation logic itself is unchanged
- Current status:
  - observed and documented
  - not yet fixed in code or operating-system configuration
